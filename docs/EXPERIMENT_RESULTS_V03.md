# 0.3 真实模型对照结果与失败分析

本轮从“能够调用模型”推进到一次完整、保留失败的策略比较。结果不支持 Investigator 普遍优于简单基线；检查器和标签口径自身也需要验证。

## 实验身份

- 时间：2026-10-01；模型：`deepseek-flash`，关闭思考模式，每次输出上限 4096 token。
- 8 个案例、4 个策略、每格 1 次，共 32 次尝试，全部按计划执行；不是 32 个独立故障。
- 正式实验发出 100 次 API 请求，内置重试关闭；已返回用量合计 468,960 token。有 1 次工具调用响应未通过协议校验，`usage_complete=false`，因此总计费 token 未知，468,960 仅为已知部分。
- 正式实验采用每个 Agent 最多 6 轮、32 次工具调用；两种固定策略各 1 次模型调用。共同观测预算为 24,000 字符/100 条记录交付。
- [执行前协议](EXPERIMENT_V03.md)、[全部结果与逐案例入口](../eval/results/v03/README.md)、[冻结源码和参数](../eval/results/v03/experiment.json)、[原始汇总](../eval/results/v03/summary.json)。导出包包含冻结的 16 个 Python 模块、8 份快照、每次状态、评分和轨迹，不包含密钥或内部消息历史。

## 按来源与划分看结果

下表是原先冻结评分规则的通过数，**不是经全面语义审阅后的诊断正确数**。后文列出的检查器误报和标签争议没有被悄悄修正进这些分数。

| 数据层 | 案例数 | single-shot | fixed-workflow | ReAct | Investigator |
| --- | ---: | ---: | ---: | ---: | ---: |
| 合成开发样例 | 2 | 1/2 | 0/2 | 1/2 | 2/2 |
| 本机 HTTP 实际测量开发数据 | 2 | 0/2 | 2/2 | 1/2 | 1/2 |
| 新编制合成压力案例 | 4 | 4/4 | 3/4 | 2/4 | 2/4 |

压力案例每种策略的模型请求数依次为 4、4、17、22 次；已知总 token 分别为 16,689、16,277、55,075、100,730，其中 ReAct 的用量不完整。不能把单次调用策略的 4/4 写成泛化正确率 100%，也不能用开发样例的 2/2 宣称 Investigator 提升准确率。

当前快照规模小，固定宽查询常能把足够证据一次取回。多轮调查有额外取证、假设记录和修复成本；本轮没有证明这些成本在所有任务上值得。该结果支持保留简单基线，并进一步研究何种观测规模和不确定性才需要动态调查。

## 暴露的实际问题

1. **检查器误报。** attempt-00001 明确否定用 p95 相加推断整体延迟，0.3 规则仍将其拒绝。不能把这条计成模型数值推理错误。后续 0.3.1 修复否定范围，原记录不变。
2. **类别层次不明确。** 部分 `wrong_cause` 报告已说出配置变化造成连接池耗尽或依赖 deadline 超时，却选择泛化的 `bad_configuration`。这里混有机制/触发因素的命名争议，不能把所有字面错类当作根因没找到。0.3.1 在提示词中补充通用类别定义，不重写旧分数。
3. **证据组并非完整语义标准。** 压力案例的弃权报告有正确方向，但未满足指定证据组；某些替代引用可能同样合理。分组标注仍需审阅，不能只凭 ID 集合证明或否定语义充分性。
4. **假设门控会增加失败。** attempt-00020 的机制判断已接近正确，但支持/反证字段未按契约修正，最终耗尽步骤。显式反证并不自动提升可用性。
5. **已通过报告仍有文字错误。** 包括把 p95 说成中位数、比较大小错误、服务与状态码混淆等，部分未被有限规则捕获。规则“没有发现问题”不等于全部陈述正确。
6. **注入评测需检查是否实际暴露。** 某个 Agent 未读取含攻击的日志，不能因此宣称它抵抗了提示注入。另一个固定策略确实看到攻击文本且没有遵从，但取证在模型调用前已经完成，不能证明自主调查抵抗取证劫持。
7. **响应协议失败没有被隐藏。** attempt-00032 的 `invalid_tool_call` 保留在分母及原轨迹，没有补跑替换，也没有把未知用量记成零。

逐份依据见 [开发/本机案例审阅](DEV_LAB_REVIEW_V03.md) 与 [压力案例审阅](CHALLENGE_REVIEW_V03.md)。这些是同一协作体系的事后审阅，不是独立人工盲评。标签争议和检查器误报说明本轮排名也受评分口径影响。

## 开发联调与原始失败回放

首次原始 inc001 报告在 0.3 的检查下检出比例、统计口径和 p95 聚合三类风险。保留旧 evaluation.json，另外生成 evaluation-v03.json，不改写原模型输出。

正式比较前的开发联调中，inc001 Investigator 使用 7 次请求、15 次工具调用，11 次查询中有 2 次为空，用量为 28,037 token；首次运行则是 16 次查询中 10 次为空、22,644 token。两者只是两次不同配置的单样本运行，没有控制随机性，不能把变化归因于某一个改动，也不能据此宣称降本。

## 0.3.1 定向开发回归（单独实验）

在原结果归档后，修复数值规则的 p95 否定范围，并在提示词中区分失败机制与配置触发因素。按 [事前计划](EXPERIMENT_V031.md) 仅在已知开发案例 inc001 上运行三种策略各一次，使用 11 次请求、42,747 个已返回 token，用量完整。加上前置联调的 7 次和正式实验的 100 次，本轮共 118 次请求，未超过 120 次上限。

| 策略 | 请求数 | 返回 token | 原预算内结果 |
| --- | ---: | ---: | --- |
| single-shot | 1 | 3,641 | 拒绝；再次写出“容量减半（100→20，相对原值降 80%）”，是真实的数值自相矛盾 |
| ReAct | 4 | 12,479 | 自动检查通过，根因机制和组件匹配 |
| Investigator | 6 | 26,627 | 自动检查通过，根因机制和组件匹配 |

[三次完整记录和冻结实现](../eval/results/v031-regression/README.md)。旧 0.3 attempt-00001 的 [零调用审计回放](../eval/results/v031-regression/audit-replay.json) 在规则 1.0.1 下不再误拦 p95 否定句；这只验证误报修复，旧报告仍有类别不匹配，原状态和分数均未更改。

事后阅读仍发现两个自动检查未覆盖的问题：ReAct 把“尚未确认是否同窗口、同分母”写成确定的“来自不同窗口/分母”；Investigator 写出“端点可达（连接建立后被池上限阻塞）”，但现有证据只说明池连接获取失败、事务未开始，不能证明失败请求已经建立连接。故两个自动通过不能称为全面语义正确。这个案例早已用于开发，本轮也同时改了规则和提示词，**不能据此推断单个机制的效果或未见场景的提升**。

## 复现

在项目根目录配置 `.env` 后，可核验已导出数据而不调用模型：

```powershell
python -m opslens benchmark --manifest eval/results/v03/manifest.json --dry-run
```

要复现 0.3 的实现条件，需要使用导出包 `source/opslens/` 下的冻结源码，当前 0.3.1 已包含后续修复；API 模型本身仍可能随供应商升级或采样发生变化。重新运行会产生费用和不同输出，应指定新的空输出目录，保留全部尝试。当前源码上的重跑不能冒充原版本重复实验。
